# 系统架构

## 请求链路

```text
浏览器
  │
  ▼
Nginx ── 静态文件
  │
  ▼
Gunicorn / Django ── MySQL
  │                    ├─ 视频与授权码
  │                    ├─ 会话与观看记录
  │                    └─ 系统设置与审计
  │
  └── Redis ── Celery Beat ── Celery Worker ── FFprobe / FFmpeg
                                                │
/video 原视频 ──────────────────────────────────┤
                                                ▼
                                  /var/lib/private-video/hls
```

## 视频处理

1. 管理员通过页面上传MP4，或维护人员将文件放入 `/video`。
2. Beat每分钟触发扫描。
3. 文件连续扫描稳定后进入转码队列。
4. Worker用FFprobe读取媒体信息，用FFmpeg生成fMP4 HLS。
5. 完成后更新视频状态和HLS相对路径。

## 播放授权

1. 观看者提交10位授权码。
2. IP黑名单中间件对标准化客户端IP执行正则完整匹配，命中时返回HTTP 403。
3. Django归一化授权码后计算HMAC摘要并查找记录。
4. 校验授权码有效期、删除状态、视频共享状态和转码状态。
5. 创建带随机令牌的播放会话，并把令牌放入 HttpOnly Cookie。
6. HLS清单被动态重写，每个媒体资源URL带短期签名。
7. Nginx仅通过内部路径发送HLS文件，原始目录不公开。

## 安全边界

- 授权码明文不入库
- 管理操作受Django staff权限、会话和CSRF保护
- 上传只接受MP4并执行多层校验
- 文件路径由服务端生成
- 授权尝试按IP限流
- 系统设置支持经语法校验的正则IP黑名单
- 播放活动和管理员操作均记录审计

浏览器必须接收媒体数据才能播放，因此系统不能从技术上保证视频绝对不可提取或录屏。
