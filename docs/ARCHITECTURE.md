# 系统架构

## 1. 架构目标

系统在一台或多台受控Linux服务器上提供两类凭授权码访问的内容：

- 私密视频：原视频不直接公开，转为HLS后通过播放会话和短期签名访问。
- 私密聊天：消息持久化到MySQL，并通过Redis Channel Layer实时广播。

公开入口只有 `/`。访问者输入10位授权码后，系统在视频授权码与聊天室授权码之间进行全局查找，不通过不同公开路径区分业务类型。

## 2. 运行拓扑

```text
浏览器
  │
  ▼
Nginx
  ├── /static/ ───────────────────────────────► 静态文件
  ├── HTTP ──► Gunicorn :8008 ──► Django ─────► MySQL 8
  ├── /ws/chat/ ──► Daphne :8009 ──► Channels ─► Redis Channel Layer
  └── /_protected_hls/（仅internal）────────────► HLS目录

Celery Beat ──每分钟──► Celery Worker
                            ├──► 扫描 /video
                            ├──► FFprobe读取媒体信息
                            └──► FFmpeg生成 /var/lib/private-video/hls
```

## 3. 组件职责

| 组件 | 职责 |
| --- | --- |
| Nginx | TLS终止、静态文件、授权接口限流、WebSocket升级、内部HLS文件发送 |
| Gunicorn | Django HTTP页面、授权、管理端、历史记录和播放接口 |
| Daphne | `/ws/chat/` WebSocket连接 |
| MySQL | 视频、授权摘要、播放会话、聊天消息、参与记录、系统设置和审计的持久化 |
| Redis | Django共享缓存、Celery Broker/结果、Channels广播；不作为聊天记录唯一存储 |
| Celery Beat | 每60秒调度视频目录扫描 |
| Celery Worker | 文件扫描、FFprobe检测和FFmpeg转码 |

生产中对应4个systemd应用服务：

- `private-video-web`
- `private-video-chat`
- `private-video-worker`
- `private-video-beat`

## 4. 统一授权流程

### 4.1 公共入口

1. 请求先经过IP黑名单中间件。
2. 访问者在 `/` 提交10位授权码。
3. 系统标准化授权码并计算HMAC摘要。
4. 系统分别查询有效视频授权码和开放聊天室授权码。
5. 找到且只找到一个目标时，创建对应会话并跳转。
6. 无效、未生效、过期、删除、停止共享、关闭聊天室或历史冲突码均拒绝访问并记录安全事件。

未删除的视频授权码与聊天室授权码在创建和轮换时进行跨表唯一性检查。视频授权码删除后释放码值，可以创建一条新的授权记录复用；旧记录和既有观看历史不会被改写。

### 4.2 视频播放

1. 校验授权码有效期、删除状态、视频共享状态和转码状态。
2. 创建随机播放令牌；数据库只保存令牌摘要，浏览器得到HttpOnly Cookie。
3. 观看页请求动态HLS清单。
4. Django重写清单，为初始化片段和媒体分片生成短期签名URL。
5. 分片通过Django校验会话和签名后，使用Nginx `X-Accel-Redirect` 进入内部HLS路径。
6. 播放开始、心跳、暂停、跳转和结束等事件更新MySQL记录。

删除授权码或停止视频共享会撤销已有活动播放会话。

### 4.3 私密聊天

1. 聊天授权成功后，系统以HttpOnly临时身份标识、IP和标准化设备特征识别同一浏览器；匹配时复用 `ChatParticipant`，否则创建参与者并分配聊天室内唯一昵称和随机头像。
2. 临时身份Cookie和访客会话Cookie都使用根路径，使再次授权、聊天室HTTP接口和 `/ws/chat/` 握手携带所需令牌。
3. WebSocket连接校验来源、聊天室状态、访客令牌、IP一致性和IP黑名单。
4. 消息通过长度、频率和会话校验后先写入MySQL。
5. 数据库提交成功后，消息才通过Redis Channel Layer广播。
6. 首次加载最近50条；`before`游标向前加载，`after`游标用于断线补拉。
7. WebSocket不可用时，前端退回HTTP轮询获取新消息。
8. 图片通过带CSRF和访客会话的HTTP接口上传，校验大小与真实像素后统一转码为WebP；消息先写入MySQL，再向聊天室广播。
9. 图片文件保存在受保护目录，读取时再次校验聊天室访客会话或staff身份，再由Nginx内部路径发送。

更换聊天室授权码、关闭聊天室或参与者主动退出都会撤销现有访客会话。退出操作使用POST与CSRF校验并清除访客Cookie。

## 5. 视频文件生命周期

1. 管理员上传MP4，或维护人员将媒体文件放入 `/video`。
2. Web上传先写入临时文件，校验成功后使用随机物理文件名原子移动。
3. 目录扫描发现文件后记录大小和修改时间。
4. 文件连续达到配置的稳定扫描次数后进入Celery队列。
5. Worker用FFprobe读取容器、视频轨道、分辨率和时长。
6. FFmpeg生成fMP4 HLS。
7. 成功后视频变为“可播放”；失败时保存错误状态供管理员排查。

原视频目录和HLS目录都不得配置为公开静态目录。
聊天图片目录同样不得公开；外部请求只能经过Django授权后的 `X-Accel-Redirect` 内部路径。

## 6. 数据与状态

- MySQL是业务与审计数据的事实来源。
- Redis缓存可重建，Channel Layer消息不替代MySQL聊天记录。
- 授权码使用HMAC摘要完成校验，并额外保存由独立环境密钥保护的加密密文，以便staff管理端回显；播放令牌和聊天访客令牌明文不入库。
- 聊天临时身份只在浏览器保存随机明文，数据库保存HMAC摘要与设备特征摘要；清除Cookie、使用新浏览器或IP/设备特征变化会被视为新参与者。
- 系统名称和IP黑名单保存在 `videos_systemsettings` 单例记录中。
- 聊天最后发言时间和消息数通过消息聚合计算，避免重复统计字段漂移。
- 数据表清单和迁移规则见 [数据库手册](DATABASE.md)。

## 7. 管理界面边界

- 所有管理端写操作要求staff登录、POST、CSRF、输入校验和管理员审计。
- 管理端一级菜单为私密视频、私密聊天、系统设置、系统管理。
- 统一授权入口、视频观看页和聊天室页显式隐藏管理员导航，即使浏览器中同时存在staff会话。
- 系统设置是无二级菜单的直接入口。

## 8. 安全边界与限制

- 客户端IP默认使用连接地址；仅在 `TRUST_PROXY_HEADERS=1` 时信任Nginx写入的 `X-Real-IP`。
- IP黑名单规则按标准化IP执行完整匹配。
- Nginx和应用层共同限制授权及聊天发送频率。
- 上传路径、HLS路径和清单内文件名均限制在配置目录中。
- 浏览器必须接收媒体数据才能播放，系统不能保证视频绝对无法提取或录屏。
- HTTPS、Secure Cookie、可信反向代理和受限的服务监听地址属于生产安全基线，详见 [部署手册](DEPLOYMENT.md) 与 [安全策略](../SECURITY.md)。
